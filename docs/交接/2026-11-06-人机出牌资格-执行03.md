## 交付范围与尚未解决的原现象

用户明确确认，观察到的提前出牌发生在骰子或发牌动画尚未结束时。

当前实际实现中，服务端在 `start/next` 内同步准备完整手牌，并立即进入规则引擎的 `discard` 阶段；客户端骰子和发牌是稍后播放的展示。人机庄家因此已经取得服务端合法出牌权，650ms 调度到期后便能行动，早于本地开场展示完成。这与“尚未点击开始对局，等待房间中的人机已经行动”不同。

项目没有开场完成通知。执行过程中已向用户说明，要精确跟随动画完成放行，需要最小的服务端衔接。用户明确选择：**不增加通知，仅修复校验并记录衔接缺口**。

因此，本版本只交付权威阶段校验、任务归属校验和生命周期隔离；不增加确认协议、等待标志或固定延时。**骰子/发牌展示未结束而服务端已经合法出牌的原现象仍可能发生，本次不将其描述为完全修复。**

## 静态定位的实际调用链

1. `RoomService.create()` 创建 `game:null` 的房间。
2. `addBot()` 只填充人机座位并置自动准备，之后调用 `_changed()`；`ready()` 也会调用 `_changed()`。两者均可能进入 `_scheduleBot()`，但没有有效 `room.game` 时 `_botTurn()` 不允许安排人机任务。
3. 房主调用 `start()`，校验四席、连接及准备情况后构造 `MahjongGame`。构造器同步调用 `newRound()`，发十三张手牌并由庄家补第十四张；此时引擎已进入 `discard`。
4. `start()` 处理携带积分与轮庄，再通过 `_changed()` 广播并调度；`next()` 也在 `newRound()` 后走此入口。如果庄家是人机，不要求真人先出牌。
5. `_scheduleBot()` 使用房间专属 timeout，按原 `botDelayMs` 安排行动。回调依据现有 `getActions()`、`_botClaim()`、`chooseDiscard()` 做决策，最终由 `game.applyAction()` 或原有流局收尾更新权威状态。
6. 客户端 `roomChanged/render/renderDiceIntro` 和开局发牌模块只播放本地表现，没有向服务端报告动画完成。本版本不修改这条链路。

## 修改文件与关键实现

### `engine.js`

新增 `hasDiscardTurn(player)`，直接复用已有状态字段，不新增游戏阶段或出牌权标志：

- 玩家编号有效。
- 阶段确为 `discard`。
- `phase.seat` 与 `current` 均指向该玩家。
- `pendingDiscard` 为空，未处于待响应弃牌窗口。
- `result` 和 `winner` 均为空，未保留结算状态。

普通 `discard()` 在移除手牌、写入牌河之前使用此校验；`getActions()` 和本家自摸/杠的执行入口也使用同一出牌权判断。本地引擎原有自动步骤在进入普通回合分支前同样使用该判断，避免无普通牌时的流局收尾绕过权限。吃碰杠胡的抢牌响应仍保留原 `claim` 分支，不要求该玩家是 `current`。

### `src/server/rooms.js`

- 真人 `action()` 入口仅接受 `discard/claim` 阶段且未结算的游戏，保留原版本号、请求编号去重和引擎动作校验。
- `_botTurn()` 在安排和执行时共用：核对房间实例仍有效、未过期、未到断线清理期限、四席连接有效、游戏未结算；普通回合复用 `hasDiscardTurn()`。响应窗口核对实际 `pendingDiscard` 与阶段记录一致，再保留原有响应资格及距离顺序。
- 每个任务使用唯一对象 `room.botTask`，记录游戏对象、`round`、`wallInfo` 对象、阶段对象、玩家及座位对象。它只控制异步任务归属，不替代或复制游戏阶段。
- `_botTaskValid()` 同时核对任务对象、牌局、轮次、同局重发时替换的 `wallInfo`、阶段身份和对应人机座位，并重新读取 `_botTurn()`。
- 同一仍合法的任务不重复安排；窗口变化时取消旧任务，从当前有效状态安排新任务。timeout 回调还校验自身 timer 句柄，旧回调不能清空或执行新任务。
- 回调开始及最终写入之前分别校验。原有无普通牌流局收尾也纳入最终校验，不能绕过任务有效性检查。
- `_cancelBot()` 同时清理房间自己的 timer 与 task。在 `start/next` 替换或重置游戏之前、`_carryGame()` 清空游戏之前主动取消。结束、暂停和身份变化继续经 `_changed()` 取消或替换任务；销毁继续使用 `_dispose()` 清理，不影响其他房间。
- 当前人机策略是同步调用，没有新增 `await`、外部依赖或策略变更。

## 正常行动如何继续

`start/next` 在完成现有引擎初始化后仍调用 `_changed()`，由 `_scheduleBot()` 安排首次合法人机行动。人机庄家保持先手资格。后续普通回合、补牌、响应、重连恢复继续从原有状态更新入口调度；没有要求真人先行动，没有关闭人机，也没有修改原有 650ms 默认间隔。

## 供审核部重点关注的路径

- 等待房间内添加/删除人机、准备或取消准备时，不应安排实际牌局动作。
- `dealing/ended`、阶段座位与当前行动者不一致、存在待响应弃牌或遗留结算时，普通出牌与自动流局不得写入状态。
- 同一窗口重复 `_changed()` 的去重；普通回合结束后新回合和同局杠后补牌的正常继续。
- 人机庄家在下一局正常先手；真人和人机混合响应时，原响应优先级、等待真人响应和抢胡处理保持原逻辑。
- timeout 已安排后换局、同局重发、替换游戏、断线、离房、移除座位、房间销毁，以及其他房间同时运行的隔离。
- 再次确认原现象仍属未处理范围：服务端已经进入 `discard`，而客户端仍在播放开场时，合法人机仍会行动。

以上是交接关注项，执行部未运行这些路径或安排复查。
