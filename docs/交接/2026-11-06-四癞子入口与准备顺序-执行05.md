## 规则来源与恢复边界

执行基线未保留独立四癞子注册项。沿 Git 历史定位到真实实现：`5e90ec3` 使用引擎参数 `wildOwner`，让指定座位从十三张起手牌中取得四张实际癞子；`3189337187075a6eaf918de6ece0c5bc78161ffb` 随后删除该规则及参数。

本次恢复该参数和发牌语义，按新需求增加一名真人与三个人机的权威开局限制。没有发明模式字符串、改变胡牌条件、计分、人机策略、骰子结果或附加概率效果。普通开始明确传 `wildOwner:null`。

恢复后的引擎从真实牌墙中取出四张癞子，纳入目标座位原有十三张起手牌，不额外增加四张牌；庄家原有补第十四张、轮庄与后续摸打规则保留。如果核心所需实物牌异常不足，抛出错误，不悄悄退回普通发牌再宣称四癞子成功。

## 两条准备入口与两种开局

### 人机快捷入口

1. 未在房间时，使用现有 `create` 建立自己的普通等待房间；恢复旧会话期间不新建房间。
2. 已有房间时，只允许自己的、尚未开始且没有其他真人参与的等待房间；已有的人机保留，只向合法空位调用原有 `addBot`。
3. 每个异步步骤后重新读取当前房间、座位及权限。其他真人加入、阶段改变或任务取消时停止补位，不移除或替换真人。
4. 补齐三个人机后，通过原有 `ready(true)` 完成真人准备，再读取服务端有效快照。
5. 准备流程结束后停留在房间。**不调用 `start`，不自动普通开局。**

### 手动补位

手动添加仍调用现有 `addBot`；事件接入同一准备函数，只添加用户选择的空位，不自动补满其他座位。恰好形成一名真人和三个人机时，通过原有 `ready(true)` 完成该真人准备。多真人房间不自动替其他真人准备。

之后由当前快照重新计算资格，满足条件即显示四癞子入口，不要求重进页面。如果真人主动取消准备，入口重新隐藏，按原准备规则处理。

### 开局选择

- “开始游戏”：`startRoom(false) → network.start(null) → RoomService.start(...,{wildOwner:null})`，使用普通随机发牌。
- “四癞子爽局”：`startRoom(true) → network.start(room.seat) → RoomService.start(...,{wildOwner:实际绝对座位})`，由服务端校验后传给 `MahjongGame`。
- 按钮出现本身没有开局副作用。进行中和结算阶段隐藏此入口，不接受通过 `start` 切换现有对局模式。

## 资格条件与共同代码

新增 `src/domain/room-start.js`，由服务端与前端共同导入：

- `isSoloHumanBotTable(seats,player)`：参与座位必须完整四席，指定座位为真人，其余三席的真实 `bot` 字段均为 `true`。
- `canPrepareBotRoom(room,player)`：等待阶段、未暂停、本人是房主及参与真人，其余位置只能是空位或真实人机。断线真人仍是占座真人，不能被当成空位。
- `canChooseFourWilds(room,player)`：在上述条件上要求启用现有癞子规则、四席均连接且已准备，并恰好为一名真人和三个人机。

快照 `room.fourWildsReady` 是服务端每次 `snapshot()` 根据这些字段计算的能力/资格结果，不写入持久房间状态。前端还要求当前连接有效、相同资格函数成立、没有补位未完成，并在请求期间禁用操作；不根据是否点击过快捷入口或是否曾经有三个人机决定显隐。

服务端与快照座位均由同一函数处理：服务端 `null` 和快照 `occupied:false` 是空位；断线真人仍是 `bot:false` 的参与者。当前项目没有独立观战身份，新逻辑也不把未占座者算作唯一真人。

人员移除、加入、权限、准备、连接变化，以及刷新和重连，都沿现有快照更新进入 `updateRoom()`，实时重算入口。不把结束、暂停或断线等同于可以选模式的等待阶段。

## 服务端校验与模式锁定

`RoomService.start()` 继续同步执行房间、身份、房主、四席、连接和准备检查。请求仅接受既有规则参数 `wildOwner`：

- `null` 表示普通开始。
- 非 `null` 必须严格等于发起请求的已认证真人房主绝对座位，并通过共同的一真三机资格判断。
- 未知开局参数、多人真人构成、未准备或已开局都不能启动四癞子。

校验、实例化与模式写入在同一同步调用中，没有异步间隙；第一个开局成功后 `room.game` 已存在，后续普通/四癞子请求统一被原开局检查阻止。

模式实际保存在游戏对象的历史 `wildOwner` 参数中，快照 `room.wildOwner` 从真实游戏对象读取并映射视角。下一局沿用已锁定参数并再次核对四癞子参与构成；不通过界面标记改变规则。退出后清空游戏、重建房间或从等待房间普通开始时，新实例明确使用 `null`，不从 `carry` 或本地存储继承四癞子配置。

补位及准备阶段 `room.game` 仍为空，原有 `_botTurn()` 不安排实际出牌；仅用户选定开局并通过服务端进入现有合法阶段后，才由原 `_changed → _scheduleBot` 调度。

## 异步、失败、退出与互斥

- `roomOperationGeneration` 与既有 `roomBusy/network.busy` 管理普通开始和四癞子开始的互斥及处理中显示，连续或交叉点击不并发提交新的开局。
- `botPreparation` 仅管理当前异步工作归属和取消，不作为模式资格来源。每次补位后检查有效房间、实际角色、阶段和任务身份。
- 准备期间保留可操作的“退出房间”；点击后取消准备任务，再等待在途命令完整结束并提交原 `leave`。
- 网络层的完成 Promise 包含命令失败后的状态读取和清理。退出中的旧补位响应不会再应用到页面，也不能继续提交准备或开局；退出完成后由现有会话代次隔离旧响应。
- 建房回复也核对代次与身份，旧回复不能把已离开的页面带回旧房间。
- 开局/准备失败后重新读取有效状态；读取失败时走现有重连。恢复动作仍核对原房间，旧失败回调不重连或操作后来进入的其他房间。
- 没有强制锁房、踢人、新的准备服务端接口或任意固定等待时间。

普通开始和四癞子使用相邻的稳定双栏区域，分别标注“普通规则”和“起手四癞 · 人机专属”。四癞子不满足条件时按钮为真正隐藏，空位置不绘制灰色按钮；预留区域避免其出现时挤压普通开始或座位信息。“退出房间”始终保留独立位置。
